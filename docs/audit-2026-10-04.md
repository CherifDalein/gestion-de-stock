# Audit du projet gestion-de-stock — 4 octobre 2026

> Les constats ci-dessous décrivent l'état lors de l'audit initial. Le suivi des corrections figure à la fin du document.

## Conclusion

Le projet démarre après l'ajout de `@Entity` à Fournisseur, mais présente des problèmes de contrôle d'accès, de sécurité des formulaires et d'intégrité du stock et des paiements. Il ne devrait pas être exposé à des utilisateurs non fiables avant correction des priorités ci-dessous.

40 constats : **2 critiques (dont un risque conditionnel lié à des secrets), 10 élevés, 20 moyens, 8 faibles**. La gravité mesure les conséquences dans une application partagée ; elle ne constitue pas une note CVSS.

## Périmètre et méthode

Revue des 44 sources Java (dont le test), des 28 modèles HTML, des scripts, du schéma SQL, de Gradle, de la configuration et des fichiers suivis par Git. Les ressources CSS et les démonstrations du thème ont été examinées pour leur rôle et leur intégration, sans audit ligne par ligne des bibliothèques tierces. Aucun fichier applicatif n'a été modifié pendant cet audit ; ce rapport est le seul ajout au projet.

Constats distingués entre preuve directe, reproduction isolée et risque déduit du code. Pas de modification de la base, de création de comptes, de test destructif ou d'attaque sur une application déployée. Les permissions effectives MySQL, les données existantes, le proxy/TLS, les sauvegardes et les paramètres de production ne sont pas certifiés. L'inventaire des CVE n'est pas exhaustif.

Vérifications :

- Compilation et démarrage réussis lors de la correction précédente ; démarrage effectué avec `ddl-auto=none`.
- `./gradlew test --offline`, puis `./gradlew test` : échec de résolution des trois dépendances de test, avant exécution des tests.
- Dépendances réellement résolues : Spring Boot 3.2.5, Spring Framework 6.1.6, Spring Security 6.2.4, Hibernate 6.4.4.Final, Tomcat 10.1.20.
- Sonde Java sans base : DataBinder accepte `achat.id`, `lignes[0].id` et `fournisseur.nom` ; un Produit avec prix négatif, stock négatif et nom absent produit **zéro violation** Bean Validation.
- Sonde BCrypt : un mot de passe correct de 72 caractères et le même préfixe suivi d'un suffixe différent sont acceptés par `matches`.
- Sonde Node avec DOM simulé : le nom produit est inséré comme HTML ; après deux ajouts de 100, le total vaut 200 mais le versement suggéré reste 100 ; après suppression et ajout, les indices restants sont `1,2`.
- Un mot de passe commenté et un cookie JSESSIONID figurent aussi dans la révision Git HEAD. Leurs valeurs ne sont pas reproduites.

## Risques critiques

### 01 — Inscription publique donnant le rôle administrateur

**Preuve directe.** `SecurityConfig.java:21` autorise `/register` sans authentification ; `AuthController.java:22` traite l'inscription ; `UtilisateurService.java:42` attribue toujours `Role.ADMIN`.

Toute personne pouvant atteindre l'application et s'inscrire peut ensuite gérer produits, partenaires et ventes, et accéder aux achats et à la caisse. Cela rend les restrictions ADMIN pratiquement inutiles.

**Correction :** réserver la création de comptes à un administrateur, ou utiliser invitations et rôle minimal. Prévoir une procédure distincte pour le premier administrateur.

### 02 — Secret et cookie de session conservés dans Git

**Présence confirmée, validité inconnue.** `src/main/resources/application.properties:33` contient un mot de passe de base distante dans un commentaire. `cookie.txt:5` contient un JSESSIONID. Les deux sont présents dans HEAD.

Commenter un secret ne le protège pas. Le risque est critique si le mot de passe est encore valide et permet l'accès à une base sensible. Le cookie peut permettre une reprise de session tant que celle-ci reste valide ; sa validité n'a pas été testée.

**Correction :** révoquer le mot de passe concerné, invalider la session si nécessaire, utiliser des variables d'environnement et retirer ces valeurs du dépôt et de son historique. Vérifier aussi les copies distantes. Nettoyer Git sans rotation ne suffit pas.

## Risques élevés

### 03 — CSRF désactivé et suppressions via GET

**Preuve directe.** `SecurityConfig.java:18` désactive CSRF pour une application authentifiée par session. Les suppressions utilisent GET dans `ProduitController.java:53`, `ClientController.java:54`, `CategorieController.java:51` et `FournisseurController.java:42`.

Un site tiers peut tenter de faire exécuter des actions par le navigateur d'un utilisateur connecté. Les conditions dépendent notamment des cookies et de SameSite. Les URL GET peuvent aussi être déclenchées par des outils de préchargement ou de vérification des liens.

**Correction :** réactiver CSRF ; utiliser POST ou DELETE pour supprimer, avec jeton et confirmation dans l'interface. SameSite ne remplace pas cette protection.

### 04 — Injection HTML et XSS stockée dans les paniers

**Chemin confirmé par code et sonde DOM ; exécution dans un navigateur non testée.** `panier.js:37` utilise `innerHTML` avec `pNom`, et `achat.js:18` / `:39` utilisent une chaîne HTML et `insertAdjacentHTML`. Le nom provient de `data-nom`, lui-même issu d'un produit enregistré.

Thymeleaf échappe correctement l'attribut initial, mais `getAttribute` récupère ensuite la valeur décodée, réinterprétée comme HTML. Un nom contenant une balise avec gestionnaire d'événement peut conduire à l'exécution de JavaScript lorsqu'un utilisateur ajoute le produit au panier.

**Correction :** construire les éléments avec `createElement`, placer les noms dans `textContent`, et ajouter les événements avec `addEventListener`. Ne pas interpoler de données métier dans du HTML ou du JavaScript.

### 05 — Liaison directe des formulaires aux entités persistantes

**Liaison reproduite ; conséquence en base déduite, non exécutée.** `AchatController.java:46`, `VenteController.java:41` et les contrôleurs CRUD prennent des entités avec `@ModelAttribute`. Aucune liste de champs autorisés ni DTO d'entrée n'est définie. La sonde accepte des identifiants d'achat et de ligne pourtant absents du formulaire normal.

Un appelant peut soumettre un identifiant existant à une route de création. `repository.save` peut alors effectuer une fusion au lieu d'une création, tandis que les services appliquent les mouvements de stock et de caisse comme une nouvelle opération. Des propriétés imbriquées sont également exposées au binding.

**Correction :** DTO explicites sans identifiants internes sur les créations, chargement des relations depuis leurs identifiants, rejet des champs imprévus. Sur modification, charger l'entité puis appliquer uniquement les champs autorisés.

### 06 — Stock vulnérable aux opérations simultanées

**Risque déduit du code.** `VenteService.java:43` lit, vérifie puis remplace le stock ; `AchatService.java:38` et `:73` suivent un schéma similaire. `Produit.java` ne porte pas `@Version` et `ProduitRepository.java` n'utilise aucun verrou.

Exemple : deux ventes lisent chacune 5 unités disponibles, vendent 4 unités et peuvent enregistrer chacune un stock final de 1. Les deux ventes existent, mais le stock ne reflète pas les 8 unités vendues. `@Transactional` ne suffit pas à éviter cette perte de mise à jour.

**Correction :** verrouillage optimiste avec gestion des conflits, verrou pessimiste, ou mise à jour atomique conditionnelle. Vérifier aussi les achats et corrections concurrents.

### 07 — Modification directe du stock sans mouvement associé

**Preuve directe.** `ProduitController.java:69` transmet le Produit à `ProduitService.java:24`, qui sauvegarde aussi sa quantité. Le formulaire `produits/modifier.html:48` expose ce champ.

Un changement manuel écrase le stock sans journal, justification ni rapprochement avec achats et ventes. Un formulaire ouvert avant une vente peut aussi réécrire une ancienne quantité.

**Correction :** sortir la quantité du formulaire de modification générale ; prévoir un ajustement de stock dédié, transactionnel, daté et attribué à un utilisateur.

### 08 — Validation des produits absente

**Reproduit.** `Produit.java:15` à `:27` ne définit aucune contrainte de validation. Le `@Valid` des contrôleurs ne rejette donc ni nom vide, ni prix négatif, ni stock négatif ou nul.

Les ventes peuvent ensuite provoquer des erreurs de calcul sur des valeurs nulles ; les produits invalides contaminent les traitements métier. Les attributs HTML `required` ne protègent pas les requêtes fabriquées.

**Correction :** contraintes serveur sur noms, références, prix, quantité et relations ; règles métier dans les services ; contraintes SQL adaptées. Définir explicitement si un prix nul est autorisé.

### 09 — Un paiement d'achat devient impossible après consommation du stock

**Preuve directe du chemin métier.** `AchatService.java:73` à `:84` retire toutes les anciennes lignes et exige que le stock actuel couvre leur quantité, même lorsque seule la somme versée change.

Exemple : achat de 10 unités, puis vente de 8. Il reste 2 unités. Augmenter simplement le montant payé échoue car le service tente d'abord de retirer les 10 unités de l'achat initial.

**Correction :** séparer le paiement de la modification des lignes ; pour les changements de quantité, traiter les différences par produit plutôt qu'annuler puis rejouer intégralement l'achat.

### 10 — Dettes enregistrées sans parcours de règlement complet

**Manque fonctionnel confirmé dans les routes et services.** Les ventes acceptent un paiement partiel, mais aucun endpoint ne permet d'enregistrer un versement ultérieur. Les achats utilisent la modification globale, affectée par le problème 09. Aucune entité de paiement distincte n'existe.

Une créance peut rester ouverte sans moyen normal de la solder. Les dates et auteurs des règlements ne sont pas représentés indépendamment du document initial.

**Correction :** paiements séparés liés à l'achat ou à la vente, chaque paiement créant son mouvement de caisse. Prévoir les remboursements et annulations selon les besoins métier.

### 11 — Version BCrypt concernée par une CVE confirmée

**Version et comportement vérifiés.** Le projet résout Spring Security Crypto **6.2.4**, utilisé par `SecurityConfig.java:48`. La sonde reproduit l'acceptation d'un suffixe différent après un préfixe de 72 caractères.

L'avis officiel [CVE-2025-22228](https://spring.io/security/cve-2025-22228/) inclut les versions 6.2.0 à 6.2.9. Ce problème concerne les mots de passe longs ; il ne permet pas de deviner un mot de passe quelconque.

**Correction :** mettre à jour la pile vers une version maintenue et corrigée, avec tests de compatibilité. Ne pas choisir uniquement le premier correctif historique : [CVE-2025-22234](https://spring.io/security/cve-2025-22234/) décrit un autre défaut introduit par ce correctif. Les autres composants anciens doivent faire l'objet d'un inventaire de vulnérabilités distinct ; leur exploitabilité n'a pas été affirmée ici.

### 12 — La suite de tests ne peut pas être compilée

**Échec reproduit.** `build.gradle:41` à `:43` déclare `spring-boot-starter-data-jpa-test`, `spring-boot-starter-thymeleaf-test` et `spring-boot-starter-webmvc-test`, sans versions résolues par cette configuration Boot 3.2.5.

Gradle échoue sur `compileTestJava`, même avec accès au dépôt Maven. Aucun test n'a donc validé l'application pendant cet audit.

**Correction :** utiliser les dépendances de test adaptées à cette version, notamment `spring-boot-starter-test`, et `spring-security-test` pour les contrôles d'accès ; remettre `./gradlew test` en état de réussir.

## Risques moyens

### 13 — Politique de rôles incohérente

`SecurityConfig.java:22` réserve ventes et référentiels à ADMIN, mais laisse achats, caisse et factures à tout utilisateur authentifié (`:23`). Un CAISSIER peut donc modifier un achat mais ne peut pas enregistrer une vente. L'interface masque seulement certaines rubriques (`dashboard.html:59`).

**Correction :** définir une matrice des droits et l'appliquer aux routes et à l'interface. L'impact dépend des droits réellement souhaités pour CAISSIER.

### 14 — Email utilisateur sans unicité SQL

`Utilisateur.java:24` et `docs/database-schema.sql` n'imposent pas l'unicité de l'email. `UtilisateurService.java:33` vérifie avant insertion, sans protection contre deux inscriptions simultanées. Des doublons peuvent casser `findByEmail`, qui attend au plus un résultat.

**Correction :** normalisation uniforme, contrainte unique en base, gestion explicite du conflit et traitement des doublons existants. La présence effective de doublons n'a pas été vérifiée.

### 15 — Inscription insuffisamment validée et login normalisé différemment

`UtilisateurService.java:26` vérifie seulement que l'email n'est pas vide ; le contrôleur ne valide pas un DTO. Le nom vide et le mot de passe vide ne sont pas rejetés explicitement. `@Email` peut intervenir lors de la persistance, avec une erreur peu adaptée à l'interface. L'inscription trimme et met l'email en minuscules, contrairement au chargement utilisé pour le login (`:67`).

**Correction :** DTO validé, longueurs limites, politique de mot de passe et normalisation partagée. Le résultat des différences de casse dépend aussi de la collation SQL ; les espaces peuvent notamment provoquer un échec.

### 16 — Absence de limitation applicative des tentatives

Les chemins login et inscription ne comportent ni limitation de débit ni mécanisme visible contre les tentatives répétées. Cela facilite les essais de mots de passe et la création massive de comptes. Une éventuelle protection externe n'a pas été vérifiée.

**Correction :** limitation adaptée par compte et origine, journalisation des événements et politique évitant de bloquer durablement les utilisateurs légitimes.

### 17 — Montants représentés par Double

`Produit.java:17`, `Achat.java:19`, `Vente.java:20` et `MouvementCaisse.java:18` utilisent Double ; le SQL utilise DOUBLE. Les calculs accumulent des approximations binaires. Certains écrans testent une égalité exacte à zéro (`achats/liste.html:36`), tandis que les corrections utilisent une tolérance.

**Correction :** BigDecimal avec règle d'arrondi et DECIMAL en base, ou entiers représentant l'unité monétaire retenue. Définir la précision GNF et harmoniser saisie, calcul et affichage.

### 18 — Valeurs numériques non finies et limites non contrôlées

Les comparaisons dans `AchatService.java:136`, `:153` et `VenteService.java:81` ne rejettent pas explicitement NaN ou Infinity. NaN échappe aux tests `< 0` et `> total`. Aucune limite métier globale de quantité, total ou nombre de lignes n'est définie.

**Correction :** types décimaux validés et bornes métier ; à défaut, `Double.isFinite`. Selon le driver et la base, ces valeurs peuvent surtout provoquer un rejet SQL ; leur persistance n'a pas été testée.

### 19 — Pas d'idempotence pour achats et ventes

Les routes de création déclenchent une nouvelle opération à chaque requête. Double clic, répétition réseau ou renvoi volontaire peuvent créer plusieurs documents et mouvements. La redirection après succès ne protège pas les requêtes concurrentes.

**Correction :** identifiant unique d'opération ou jeton de soumission consommé transactionnellement ; désactivation temporaire du bouton comme aide d'interface.

### 20 — Indices incomplets après suppression d'une ligne d'achat

**Reproduit dans le script.** `achat.js:50` retire la ligne sans renuméroter les champs ; `index` continue à augmenter. Contrairement à `panier.js:119`, aucun traitement avant soumission ne reconstitue des indices consécutifs.

Des champs `lignes[1]`, `lignes[2]` peuvent laisser une première ligne vide lors du binding Spring, puis faire rejeter l'achat par la validation. Le problème concerne aussi la modification d'achat.

**Correction :** renuméroter les champs avant envoi ou utiliser un DTO avec un format de lignes explicite.

### 21 — Panier perdu après erreur métier

`achats/nouveau.html:99` et `ventes/nouveau.html` initialisent les tableaux de panier vides. Les contrôleurs renvoient ces pages après une erreur, mais elles ne reconstruisent pas les lignes soumises. Le paiement et certains champs peuvent subsister alors que les lignes ont disparu.

**Correction :** restituer les lignes du DTO et les erreurs de champs, avec un total recalculé. Une erreur de stock ne devrait pas obliger à ressaisir toute la vente.

### 22 — Suggestion de paiement incohérente et saisie décimale variable

**Suggestion reproduite.** `achat.js:65` et `panier.js:88` ne mettent le paiement au nouveau total que s'il est vide ou zéro. Après deux ajouts de 100, le total vaut 200 mais le versement reste 100. Une valeur zéro saisie volontairement peut aussi être remplacée lors d'un ajout. `ventes/nouveau.html:72` ne définit pas de `step` décimal, contrairement aux achats.

**Correction :** distinguer une valeur suggérée d'une valeur saisie ; préserver un paiement nul explicite ; harmoniser la précision des champs. Le champ en lecture seule du total doit également accepter la précision choisie.

### 23 — Suppressions de données référencées non gérées

Les services CRUD font directement `deleteById` pour des produits, clients, fournisseurs ou catégories, sans vérifier leur utilisation. Les clés étrangères du schéma empêchent normalement la suppression de certaines données utilisées ; les contrôleurs ne convertissent pas ce conflit en message utile.

**Correction :** archivage/désactivation des référentiels utilisés, contrôle des références et réponse explicite. Ne pas cascader la suppression des documents historiques pour résoudre le problème.

### 24 — Factures historiques dépendantes des données actuelles

`factures/template_vente.html:92` / `:117`, `template_achat.html:92` et les relevés cumulés utilisent les noms et coordonnées des entités vivantes. Renommer un produit ou un partenaire change la réimpression d'un ancien document.

**Correction :** conserver les informations nécessaires à l'émission dans le document et ses lignes. Les prix unitaires sont déjà conservés sur les lignes, ce qui constitue une bonne base.

### 25 — Modifier un ancien achat remplace le prix d'achat courant

`AchatService.java:95` à `:96` réapplique le prix de chaque ligne au Produit, sans comparer les dates d'achat. Une correction ancienne peut écraser le prix provenant d'un achat plus récent. Plusieurs lignes du même produit rendent aussi le résultat dépendant de leur ordre.

**Correction :** définir si ce prix représente le dernier prix chronologique, un prix de référence ou un coût moyen ; le calculer selon cette règle, indépendamment de l'ordre des corrections.

### 26 — Calculs « du jour » sans borne de fin et fuseau implicite

`MouvementCaisseRepository.java:18` / `:24` / `:27` et `CaisseService.java:48` recherchent tout ce qui suit le début du jour. Pour une date passée, les jours suivants sont inclus. Les filtres factures utilisent aussi uniquement une borne basse et `After`, qui exclut l'instant exact du début.

Les dates utilisent `LocalDateTime.now()` sans fuseau métier explicite, tandis que la connexion annonce UTC. Les effets exacts dépendent du serveur et de MySQL.

**Correction :** intervalles `[début, fin)`, fuseau métier configuré et tests autour de minuit. Clarifier également si « semaine » signifie sept jours glissants ou semaine civile.

### 27 — Un paiement null peut masquer une dette

`Achat.java:29` et `Vente.java:29` renvoient zéro dès qu'un montant est null. Un document avec total 1 000 et paiement null est donc interprété comme sans reste par ces accesseurs, alors que d'autres vues traitent null comme zéro payé.

**Correction :** définir une politique uniforme pour les anciens documents : null payé équivaut-il à zéro ou à une donnée manquante ? Contraindre les nouvelles écritures et traiter les données existantes.

### 28 — Erreurs techniques affichées et erreurs métier mal transportées

`AuthController.java:33`, `AchatController.java:55` et `VenteController.java:50` affichent directement les messages d'exception, qui peuvent contenir des détails SQL ou internes. `AchatController.java:79` concatène le message à une URL sans encodage. Plusieurs recherches d'identifiants finissent par une RuntimeException ou `Optional.get()` (`ProduitService.java:21`).

**Correction :** exceptions métier explicites, messages publics maîtrisés, logs internes, réponses 404/409 adaptées et attributs flash au lieu des messages dans l'URL. `th:text` échappe ces messages : cela ne constitue pas à lui seul une XSS.

### 29 — Configuration locale utilisée comme configuration générale

`application.properties:3` à `:12` utilise root, un mot de passe actif vide, `useSSL=false`, `createDatabaseIfNotExist=true`, `ddl-auto=update` et les requêtes SQL visibles. Aucun profil de production distinct ni outil de migration n'est fourni.

Ces options peuvent convenir à un poste local, mais ne définissent pas un déploiement maîtrisé : privilèges excessifs, absence de chiffrement de la connexion distante et évolution implicite du schéma. Le moteur local est signalé par Hibernate comme MySQL 5.5.0, sous le minimum pris en charge par le dialecte utilisé ; la version exacte du serveur reste à vérifier.

**Correction :** compte applicatif restreint, secrets externes, configuration par environnement, TLS vérifié pour les connexions distantes, migrations versionnées et validation du schéma en production. Vérifier le moteur et sa version réelle avant de choisir le dialecte. Le dialecte explicitement défini provoque aussi un avertissement de redondance.

### 30 — Tests sans isolation et couverture métier absente

`StockApplicationTests.java:6` charge tout le contexte ; aucun profil de test ni base dédiée n'est fourni. Une fois les dépendances corrigées, le test utilisera par défaut la configuration MySQL avec `ddl-auto=update`, susceptible de toucher le schéma local. Le seul test est `contextLoads` ; aucune CI n'est présente dans le dossier.

**Correction :** base isolée et données de test, tests de droits, CSRF, paiements, rollback et concurrence. La réussite de `contextLoads` ne prouve pas la fiabilité des opérations de stock.

### 31 — Chargements complets et risque de requêtes N+1

Les services listent les données avec `findAll`, et `CaisseController.java:27` charge tout le journal. DataTables pagine seulement l'affichage côté navigateur. `ventes/liste.html:74` parcourt les lignes de chaque vente pour créer toutes les fenêtres de détail ; les factures cumulées parcourent aussi les relations.

**Correction :** pagination et filtres SQL, chargement des détails à la demande, projections ou plans de chargement adaptés. L'effet sur les temps de réponse dépend du volume ; aucune mesure de charge n'a été faite. Les agrégats de caisse devraient aussi être regroupés pour éviter les lectures répétées et des valeurs prises à des instants différents.

### 32 — Tableau des achats structurellement incohérent

`achats/liste.html:14` à `:22` définit sept en-têtes, mais chaque ligne contient huit cellules : l'en-tête du total manque, décalant Verse/Reste/Statut/Actions. Des fermetures HTML sont répétées à partir de `:53`, après la fermeture du fragment. Les formulaires produits contiennent également des fermetures excédentaires.

**Correction :** rétablir un en-tête par cellule et valider la structure HTML des fragments. Le traitement précis des balises excédentaires dépend du parseur ; le décalage du tableau est visible dans le code.

## Problèmes faibles et dette de maintenance

### 33 — Fournisseur courant du produit et fournisseur d'achat désynchronisés

`Produit.fournisseur` et `Achat.fournisseur` sont indépendants. `AchatService` ne vérifie ni ne met à jour leur cohérence ; le formulaire d'achat propose tous les produits. Cela peut être voulu pour un approvisionnement multiple, mais la liste produits affiche un fournisseur unique.

**Correction :** définir la signification de cette relation : fournisseur préféré, exclusif ou dernier fournisseur. Adapter le modèle et les libellés à cette règle.

### 34 — Modification d'achat difficile à découvrir et retour de succès incomplet

`AchatController.java:61` expose une modification, mais `achats/liste.html:39` ne fournit que le lien de facture. Les attributs de succès des créations et le paramètre `success=modifie` ne sont pas affichés dans cette liste.

**Correction :** ajouter l'action appropriée et des messages de confirmation. La route existante ne suffit pas à rendre le parcours accessible.

### 35 — Documentation de démarrage pratiquement absente

README.md contient essentiellement le nom du projet, en UTF-16. Il n'explique ni Java 21, ni MySQL, ni les variables, les comptes initiaux, les tests ou les sauvegardes. Des commentaires de `application.properties` contiennent des caractères de remplacement.

**Correction :** README UTF-8 avec installation, configuration, environnement de test, commande de lancement et procédures de maintenance. Documenter le modèle SQL et ses migrations effectives.

### 36 — Ressources tierces exécutées sans intégrité vérifiée

`dashboard.html:10` et `:210` à `:213` chargent du JavaScript de CDN sans attribut `integrity`. `crossorigin` seul ne vérifie pas les octets du script. L'interface et les impressions dépendent aussi du réseau externe ; aucune CSP applicative n'est configurée.

**Correction :** ressources maîtrisées localement ou versions figées avec SRI, puis CSP compatible avec les scripts. Aucune compromission de ces CDN n'a été constatée.

### 37 — Code inutilisé et conventions incohérentes

`ProduitService.java:14` possède un constructeur qui ignore son argument, alors que l'injection repose sur le champ. `CustomAuthFailureHandler` est déclaré mais la chaîne utilise `failureUrl`. `UtilisateurService.login` double une partie du mécanisme Spring Security sans être appelé par le contrôleur. `DetailAchatRepositoory` comporte une faute dans son nom. Plusieurs injections et scripts de démonstration sont inutilisés.

**Correction :** injection par constructeur, suppression du code mort et conventions cohérentes. `@Data` sur Utilisateur inclut le hash de mot de passe dans le `toString` généré ; exclure ce champ pour éviter une fuite lors d'un futur log. Aucune fuite de hash dans les logs n'a été démontrée.

### 38 — Fonctions d'interface inachevées et informations fictives

`dashboard.html:17` affiche une recherche sans traitement ; Paramètres et Journal d'activité pointent sur `#!`. Les modèles de factures affichent des coordonnées fixes, dont un téléphone fictif (`template_achat.html:85`).
